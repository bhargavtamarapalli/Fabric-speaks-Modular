Architecture Principles</strong></h1><h2><strong>2.1  Config-First Environment Management</strong></h2><p>All environment-specific values live in config files — never hardcoded. A single Config Service merges default + environment-specific config at runtime.</p><p>  Environments</p><p>  ├── development.config.js   → local DB + Redis, Razorpay test, WhatsApp sandbox</p><p>  ├── staging.config.js       → Cloud SQL + Redis (Cloud), test API keys</p><p>  └── production.config.js    → Cloud SQL HA + Redis + all live API keys</p><p> </p><p>  Feature Flags (in config — toggle without deploy)</p><p>  features.cod            = true / false</p><p>  features.guestCheckout  = true / false</p><p>  features.whatsapp       = true / false   ← fallback to SMS if false</p><p>  features.reviews        = true / false</p><h2><strong>2.2  Repository Pattern — DB Vendor Abstraction</strong></h2><p>  Service Layer  →  Repository Interface  →  Implementation  →  DB</p><p>                    (never changes)          (swap this)        (any vendor)</p><p> </p><p>  Switch vendor = write one new implementation file + change config.db.vendor</p><p>  Zero changes to any service, controller, or API layer.</p><h2><strong>2.3  Generic Attribute Model</strong></h2><p>Product attributes stored as JSON key-value pairs. Adding Footwear or Beauty = new category config, zero schema migration on the products table.</p><h2><strong>2.4  Async-First Post-Order Processing</strong></h2><p>Order placement is synchronous only for critical path: stock reservation + payment capture + order record creation. Everything else (WhatsApp, email, push, Shiprocket shipment) goes to an async job queue. Customer sees order confirmation in &lt; 1 second regardless of downstream service latency.</p><p>  SYNCHRONOUS (&lt; 1s, order fails if these fail)</p><p>  → Stock reservation (atomic + row lock)</p><p>  → Payment capture / COD validation</p><p>  → Order record + GST invoice creation</p><p>  → Order confirmation response to customer</p><p> </p><p>  ASYNC QUEUE (non-blocking, retried on failure)</p><p>  → WhatsApp confirmation message</p><p>  → Email invoice</p><p>  → FCM push notification</p><p>  → Shiprocket shipment creation</p><p>  → Inventory stock deduction (post-payment confirmed)</p><p>  → Event tracking log write</p><h2><strong>2.5  Soft Delete Strategy (Universal)</strong></h2><p>No hard deletes on any business entity. All mutable tables carry is_deleted (boolean) + deleted_at (timestamp). Queries always filter WHERE is_deleted = false. This preserves order history, GST invoice references, and review integrity permanently.</p><h1><strong>3.
