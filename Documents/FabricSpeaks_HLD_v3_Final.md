Architecture Principles</strong></h1><p>Principles 2.1 through 2.5 from v2 are unchanged: Config-First, Repository Pattern, Generic Attribute Model, Async-First Post-Order Processing, Soft Delete Strategy.</p><h2><strong>2.6  Collection Rule Evaluation (New)</strong></h2><p>Smart Collections define product membership via rules stored as rules_json. Rules are evaluated server-side at product save and cached in Redis with 1-hour TTL. Cache is invalidated on any product update or collection config change.</p><p>  Smart Collection Rule Evaluation Engine</p><p>  ─────────────────────────────────────────────────────────</p><p>  Product saved or updated</p><p>        ↓</p><p>  Collection Service: evaluate all smart collections</p><p>  whose rules include fields that changed</p><p>        ↓</p><p>  Rebuild collection_products for affected smart collections</p><p>        ↓</p><p>  Invalidate Redis cache for affected collection slugs</p><p>        ↓</p><p>  Next page load → cache miss → fresh query → recache</p><p>  Subsequent loads → cache hit → serve immediately</p><p> </p><p>  Rule Keys Whitelist (no arbitrary code evaluation):</p><p>  fabric_type | price | category_id | in_stock | sale_active</p><p>  brand_id | gsm_min | gsm_max | is_active</p><h2><strong>2.7  Sale Price Precedence Rule (New)</strong></h2><p>Three-tier pricing hierarchy is now locked: (1) sale_price when sale_active is true, (2) price_override if set on variant, (3) base_price from product. The effective price is always calculated server-side and returned in API responses. UI never calculates price independently.</p><h2><strong>2.8  Navigation and Homepage as Config (New)</strong></h2><p>Navigation structure and homepage layout are database-driven and Redis-cached. Admin changes take effect within seconds, not deployment cycles. Cache key per nav item set is invalidated on every admin save. This means zero developer involvement for campaign launches, sale events, or seasonal homepage changes.</p><h1><strong>3.
