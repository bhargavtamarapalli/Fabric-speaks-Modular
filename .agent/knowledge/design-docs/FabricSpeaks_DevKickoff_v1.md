A PR that violates any of these will be rejected — no exceptions.</p><table><tr><td><p><strong>Why these rules exist</strong></p><p>Each of these rules exists because its violation causes a specific, serious harm:</p><p>Rules 1+2 → price manipulation or order fraud</p><p>Rule 3     → IDOR (a user accessing another user's data)</p><p>Rule 4     → SQL injection</p><p>Rule 5     → PII leaking to external monitoring services</p><p>Rule 6     → silent audit trail gaps that block compliance and debugging</p></td></tr></table><h2><strong>Rule 1 — Never Trust Client Prices</strong></h2><p>The client sends product IDs and quantities. The server calculates every rupee. No exceptions.</p><table><tr><td><p><strong>❌</strong></p></td><td><p>// WRONG — never do this</p><p>const total = req.body.total;  // trusting client</p><p>const price = req.body.price;  // trusting client</p><p>await createOrder({ total, price });</p></td><td><p>// CORRECT</p><p>const variant = await variantRepo.findById(variantId);</p><p>const price = getEffectivePrice(variant);  // server calc</p><p>const total = items.reduce((sum,i) =&gt; sum + price * i.qty, 0);</p></td></tr></table><p>getEffectivePrice() priority: sale_price (if sale_active=true) → price_override → base_price. This function lives in @fs/shared/pricing.ts and is the only source of truth.</p><h2><strong>Rule 2 — user_id Always From JWT, Never From Request</strong></h2><p>The authenticated user's ID comes from the verified JWT claims. Never from the request body, query string, or path param when scoping to the current user.</p><table><tr><td><p><strong>❌</strong></p></td><td><p>// WRONG — user can pass any userId</p><p>const userId = req.body.userId;</p><p>const orders = await orderRepo.findByUser(userId);</p></td><td><p>// CORRECT — userId always from verified JWT</p><p>const userId = req.user.userId; // set by auth middleware</p><p>const orders = await orderRepo.findByUser(userId);</p></td></tr></table><p>IDOR protection: user-scoped endpoints return 404 (not 403) when a resource belongs to a different user. This prevents existence enumeration. See Security Design Layer 2.</p><h2><strong>Rule 3 — Parameterised Queries Only</strong></h2><p>Never concatenate user input into a SQL string. Always use the pg tagged template or parameterised query form.</p><table><tr><td><p><strong>❌</strong></p></td><td><p>// WRONG — SQL injection risk</p><p>const q = `SELECT * FROM products</p><p>  WHERE slug = '${slug}'`;  // ❌ NEVER</p><p>await db.query(q);</p></td><td><p>// CORRECT — parameterised</p><p>await db.query(</p><p>  'SELECT * FROM products WHERE slug = $1',</p><p>  [slug]  // ✅ always an array of values</p><p>);</p></td></tr></table><h2><strong>Rule 4 — Throw AppError, Never Raw Errors</strong></h2><p>Services throw AppError(ErrorCode.X). Controllers catch AppError and map it to the API response envelope. Raw DB errors, Firebase errors, and Razorpay errors must never reach the client.</p><table><tr><td><p><strong>❌</strong></p></td><td><p>// WRONG — exposes internals</p><p>throw new Error('duplicate key violates unique constraint');</p><p>// or</p><p>res.status(500).json({ error: err.message });</p></td><td><p>// CORRECT</p><p>if (!product) {</p><p>  throw new AppError(ErrorCode.PRODUCT_NOT_FOUND);</p><p>}</p><p>// globalErrorHandler in api-gateway catches this</p><p>// and maps to { success:false, error:{code,message} }</p></td></tr></table><p>Sentry captures the full stack trace via Sentry.captureException() before the error is mapped. The client only ever sees the ErrorCode and a safe human-readable message.</p><h2><strong>Rule 5 — No PII in Logs or Error Context</strong></h2><p>Mobile numbers, emails, addresses, and payment details must never appear in structured logs, Sentry events, or console output.</p><table><tr><td><p><strong>❌</strong></p></td><td><p>// WRONG — PII in logs</p><p>logger.info(`OTP sent to ${mobile}`);</p><p>logger.error('Order failed', { userEmail, address });</p></td><td><p>// CORRECT — mask PII</p><p>logger.info(`OTP sent to ${maskMobile(mobile)}`);</p><p>// maskMobile('9876543210') → '98XXXXXX10'</p><p>logger.error('Order failed', { userId, orderId });</p><p>// log IDs only — never content</p></td></tr></table><p>maskMobile() and maskEmail() utilities live in @fs/shared/logger.ts. Use them. DPDPA (India) requires this. Sentry is also configured with scrubbing rules — but that is a safety net, not a replacement for correct code.</p><h2><strong>Rule 6 — Admin Mutations Must Write Audit Log</strong></h2><p>Every admin-triggered mutation (create, update, deactivate, role change, refund) must write an entry to admin_audit_log before returning. This is a compliance requirement.</p><table><tr><td><p><strong>❌</strong></p></td><td><p>// WRONG — mutation with no audit trail</p><p>await productRepo.deactivate(productId);</p><p>return { deactivated: true };</p></td><td><p>// CORRECT — audit log before return</p><p>await productRepo.deactivate(productId);</p><p>await auditLog.insert({</p><p>  adminId: req.user.userId,</p><p>  action: 'product_deactivate',</p><p>  targetType: 'product',</p><p>  targetId: productId,</p><p>  payload: { reason: dto.reason },</p><p>}); // ✅ then return</p></td></tr></table><p>AuditLogRepository.insert() is an INSERT-only method. It never updates or deletes audit records. This is enforced in the repository implementation.</p><h1><strong>5.
