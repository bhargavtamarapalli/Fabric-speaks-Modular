Executive Summary</strong></h1><p>Fabric Speaks is a fabric-first multi-brand clothing e-commerce platform targeting working men aged 25–40 in India. This High-Level Design (HLD) document defines the system architecture, service boundaries, component interactions, data flows, technology stack, and infrastructure strategy for the MVP.</p><p>The architecture is deliberately designed with three core principles:</p><ul><li>Reusability — the core engine (Auth, Orders, Payments, Inventory, Notifications) is product-agnostic and reusable for future verticals (footwear, accessories, beauty).</li><li>Replaceability — every external dependency (DB vendor, payment gateway, logistics partner) can be swapped with minimal code change via the Repository Pattern and Config Service.</li><li>Scalability — services are independently deployable, allowing individual scaling without rebuilding the monolith.</li></ul><table><tr><td><p><strong>Scope of this Document</strong></p><p>This HLD covers the MVP scope only. Post-MVP features (vendor self-onboarding,</p><p>loyalty points, AI review summarisation, affiliate management) are noted where</p><p>architectural hooks must be preserved, but are not designed in detail here.</p></td></tr></table><h1><strong>2. Architecture Principles</strong></h1><h2><strong>2.1 Config-First Environment Management</strong></h2><p>All environment-specific values (DB credentials, API keys, feature flags) live in environment configuration files, never hardcoded. A single Config Service loads the correct config based on NODE_ENV at runtime.</p><p>  Environments:</p><p>  ├── development.config.js   → local DB, Razorpay test mode, WhatsApp sandbox</p><p>  ├── staging.config.js       → cloud DB, Razorpay test mode, WhatsApp sandbox</p><p>  └── production.config.js    → cloud DB, Razorpay live mode, WhatsApp live API</p><p> </p><p>  .env files hold secrets (never committed to git):</p><p>  .env.development / .env.staging / .env.production</p><h2><strong>2.2 Repository Pattern — DB Vendor Abstraction</strong></h2><p>Business logic never communicates directly with the database. A Repository Interface defines the contract; the implementation can be swapped (MySQL → PostgreSQL → MongoDB) by changing one config line and writing one new implementation file.</p><p>  Business Logic (Services)</p><p>          ↓</p><p>  Repository Interface     ← Contract. NEVER changes.</p><p>          ↓</p><p>  Repository Implementation ← Changes when DB vendor changes.</p><p>          ↓</p><p>  Database (Cloud SQL — MySQL/Postgres, switchable via config)</p><h2><strong>2.3 Generic Attribute Model — Future-Proof Catalog</strong></h2><p>Product attributes are stored as key-value pairs, not hardcoded columns. This means adding Footwear (size, sole material) or Beauty (skin type, SPF) requires only new category configuration — zero schema migration on core tables.</p><p>  product.attributes = [</p><p>    { key: 'fabric',  value: 'linen' },</p><p>    { key: 'gsm',     value: '180'   },</p><p>    { key: 'size',    value: 'L'     },</p><p>    { key: 'color',   value: 'navy'  }</p><p>  ]</p><p> </p><p>  Future: Footwear just adds different attribute keys.</p><p>  Core schema stays identical.</p><h2><strong>2.4 Service Boundary Principle</strong></h2><p>Each service owns exactly one domain. Services communicate via well-defined internal APIs. No service reads directly from another service's database table.</p><h1><strong>3.
